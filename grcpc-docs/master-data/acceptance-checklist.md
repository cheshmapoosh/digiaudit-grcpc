# Master Data V2 Acceptance Checklist

## 1. Purpose and use

This checklist is the delivery gate for all later Master Data V2 implementation prompts.

Every checked item requires objective evidence from migrations, tests, API contract checks, UI checks, or source inspection.

The checklist must be completed without creating a legacy compatibility path.

## 2. Later implementation-prompt map

| Prompt label | Intended vertical slice | Checklist sections primarily owned |
| --- | --- | --- |
| P0 | Day-Zero foundation and API conventions | Global, Database, Flyway, Backend, Security |
| P1 | Central definitions | Database, Backend, UI, Legacy cleanup |
| P2 | Central Scope | Central Scope, Backend, UI |
| P3 | Central Coverage and Central Policy Scope | Central Coverage, Policy Scope, Security, UI |
| P4 | Local Context | Local Context, Backend, UI |
| P5 | Local Scope, Local Coverage, and Local Policy Scope | Local Scope, Local Coverage, Policy Scope, UI |
| P6 | Document and Business Revision integration | Document, MinIO, Business Revision, Security |
| P7 | Effective, Diagnostic, Roll-up, and Policy Applicability | Effective, Diagnostic, Roll-up, Policy Applicability |
| P8 | Full-stack cleanup and release verification | Legacy cleanup, Final full-stack acceptance |

## 3. Global project acceptance — P0 through P8

- [ ] The implementation follows the greenfield Master Data V2 contract rather than a legacy upgrade strategy.
- [ ] The installation target is a fresh Oracle 19c-compatible database.
- [ ] No legacy data migration is present in V2 Flyway history.
- [ ] No legacy schema upgrade path is present in V2 Flyway history.
- [ ] No compatibility view exposes a legacy Master Data table shape.
- [ ] No compatibility API aliases a legacy Master Data endpoint.
- [ ] No dual write persists the same fact to V2 and legacy Master Data tables.
- [ ] Exactly 47 business tables exist in the Master Data V2 redesign scope.
- [ ] Exactly one technical `document_temp_upload` table exists in the redesign scope.
- [ ] No extra Master Data table is introduced for convenience, caching, assignment, workflow, monitoring, audit, jobs, scheduler, or outbox.
- [ ] No Master Data business logic exists outside the Master Data domain/application boundary.
- [ ] No unnecessary duplicate domain and JPA models exist for the same V2 aggregate.
- [ ] No generic abstraction exists without multiple proven V2 use cases.
- [ ] KPI is absent from database, backend, API, permissions, UI, i18n, and acceptance fixtures.
- [ ] KRI is absent from database, backend, API, permissions, UI, i18n, and acceptance fixtures.

## 4. Database acceptance — P0 and P1

- [ ] Every V2 primary key is stored as Oracle `RAW(16)`.
- [ ] Every V2 UUID foreign key is stored as Oracle `RAW(16)`.
- [ ] UUIDs are generated by the backend before persistence.
- [ ] No V2 business id is stored as `VARCHAR2(36 CHAR)`.
- [ ] Every mutable V2 business table has `version NUMBER(19)`.
- [ ] Every mutable V2 business table has explicit lifecycle/delete metadata as cataloged.
- [ ] Every table with validity has valid-from/valid-to range protection.
- [ ] Every table with a business code has unconditional uniqueness that includes deleted rows.
- [ ] Every foreign key has an index or an equivalent leading composite index.
- [ ] Composite foreign keys enforce same-Subprocess Central Coverage.
- [ ] Composite foreign keys enforce same-context Local Coverage.
- [ ] Process and Subprocess are physically separated.
- [ ] Risk Category and Risk Template are physically separated.
- [ ] Regulation Group, Regulation, and Regulation Requirement are physically separated.
- [ ] Policy Group, Policy, and Policy Version are physically separated.
- [ ] Account Group relationships are normalized and not stored as JSON/CLOB arrays.
- [ ] No generic assignment table exists.
- [ ] No generic coverage table with caller-controlled type/id exists.
- [ ] No direct Control–Regulation table exists.
- [ ] No materialized Effective, Diagnostic, Roll-up, or Policy Applicability table exists.

## 5. Flyway acceptance — P0

- [ ] Flyway owns all V2 schema creation.
- [ ] Hibernate uses `ddl-auto=validate` for V2 runtime.
- [ ] Hibernate creates, alters, or drops no V2 table.
- [ ] Day-Zero migrations install successfully on an empty Oracle 19c database.
- [ ] Day-Zero migration order creates definitions before scopes.
- [ ] Day-Zero migration order creates scopes before coverage and policy-scope relations.
- [ ] Day-Zero migration order creates Local Context before Local Scope/Coverage.
- [ ] Day-Zero migration order creates Business Revision before Document Version revision foreign keys.
- [ ] Day-Zero migration order creates Document Link only after Document Version.
- [ ] Day-Zero migration order creates no legacy `process_node`, `risk_node`, `policy_node`, generic Objective, generic attachment, or generic assignment table.
- [ ] No V2 migration copies rows from legacy Master Data tables.
- [ ] No applied legacy migration file is edited.

## 6. Backend acceptance — P0 through P7

- [ ] Controllers are thin HTTP adapters.
- [ ] Business validation lives in Master Data application/domain services.
- [ ] Persistence repositories do not perform hidden business workflow.
- [ ] API DTOs do not expose JPA entities.
- [ ] Every Create Command is separate from every Update Command.
- [ ] Every normal read uses a dedicated Read DTO.
- [ ] Effective reads use a dedicated Effective Read DTO.
- [ ] Diagnostic reads use a dedicated Diagnostic DTO.
- [ ] Every mutable command requires version where specified by API conventions.
- [ ] Every successful mutation returns `entityId`, `revisionId`, and `version`.
- [ ] Every mutation uses standard error and validation envelopes.
- [ ] No frontend-controlled transaction order is accepted by any endpoint.
- [ ] No frontend-created Revision Content is accepted by any endpoint.
- [ ] No generic core Scope/Coverage CRUD endpoint exists.
- [ ] No `@SQLDelete` hides V2 soft delete behavior.
- [ ] Explicit delete and restore commands exist for applicable mutable aggregates.
- [ ] No direct Control–Regulation controller/action remains.
- [ ] No generic Objective controller/action remains in V2.

## 7. UI acceptance — P1 through P8

- [ ] Existing compatible FCL patterns are retained where they do not impose legacy data flow.
- [ ] Existing compatible List Report patterns are retained where they do not impose legacy data flow.
- [ ] Existing compatible Object Page patterns are retained where they do not impose legacy data flow.
- [ ] Existing compatible tree, search, selection, and expanded-state behavior is retained.
- [ ] Process and Subprocess may render in a combined tree but use separate backend entity data.
- [ ] Persian remains the default user-facing language for relevant screens.
- [ ] RTL layout remains intact on V2 pages and dialogs.
- [ ] All new visible text uses i18n keys in supported language packs.
- [ ] UI5 components are used where the existing design system provides an appropriate component.
- [ ] Every mutation UI sends required version and handles returned revision/version feedback.
- [ ] Every mutable screen offers explicit soft delete/restore behavior where applicable.
- [ ] UI contains no manual arbitrary UUID fallback for typed relationships.
- [ ] UI contains no direct final upload or standalone generic commit action.
- [ ] UI contains no dead route, page, component, store, API repository, or i18n key after each completed slice.

## 8. Document acceptance — P6

- [ ] A Document has a stable business identity separate from file content.
- [ ] A Document Version is immutable after creation.
- [ ] File-content change creates a new Document Version rather than overwriting one.
- [ ] Document Link is the only document-target controlled polymorphism.
- [ ] Document Link target types use a closed V2 aggregate allow-list.
- [ ] Document Link commands enforce resource authorization.
- [ ] Document Version creation occurs through an owning Business Command.
- [ ] No legacy `document_attachment` entity/table/API remains in V2 behavior.
- [ ] No legacy `control_document` entity/table/API remains in V2 behavior.
- [ ] Document metadata does not expose MinIO bucket, object key, credentials, or permanent URL.
- [ ] A purged Document Version produces the defined `DOCUMENT_VERSION_PURGED` error.
- [ ] V2 document UI shows immutable version history and authorized download state.

## 9. MinIO acceptance — P6

- [ ] MinIO configuration remains behind a backend storage adapter/configuration boundary.
- [ ] No storage credential is sent to the frontend.
- [ ] No permanent MinIO URL is sent to the frontend.
- [ ] Temporary upload is created before final Document creation.
- [ ] The temporary-upload initiation response contains backend-issued `tempUploadId`.
- [ ] The frontend does not create or send `tempSessionId`.
- [ ] A Temp Upload can be consumed exactly once.
- [ ] Expired Temp Upload cannot be consumed.
- [ ] Invalid Temp Upload cannot be consumed.
- [ ] Already-consumed Temp Upload returns the defined conflict error.
- [ ] Direct final upload does not exist.
- [ ] No distributed Oracle–MinIO transaction is claimed or implemented.
- [ ] Storage failure has explicit recoverable/compensating behavior without an extra outbox or job table.

## 10. Business Revision acceptance — P0 and P6

- [ ] One backend-owned Business Revision is created for every successful Business Command.
- [ ] A failed validation creates no applied Business Revision.
- [ ] The backend owns revision sequence assignment.
- [ ] The backend owns before/after snapshot creation.
- [ ] The frontend cannot create Revision Content.
- [ ] The frontend cannot send Revision Content sequence, hash, snapshot, or aggregate type.
- [ ] Applied Business Revision is immutable.
- [ ] Revision Content is immutable.
- [ ] Revision Content is limited to the approved closed aggregate-type allow-list.
- [ ] Revision domain mismatch returns `REVISION_DOMAIN_MISMATCH`.
- [ ] Missing Revision context returns `REVISION_CONTEXT_REQUIRED`.
- [ ] Idempotent retry returns the original mutation result and does not create a duplicate revision.
- [ ] Document Version creation records the owning Business Revision.

## 11. Central Scope acceptance — P2

- [ ] Central definitions are independent from Organization.
- [ ] Central Subprocess Scope is created only for an existing Subprocess.
- [ ] Central Control Scope is typed and references Control.
- [ ] Central Control Objective Scope is typed and references Control Objective.
- [ ] Central Risk Template Scope is typed and references Risk Template.
- [ ] Central Regulation Requirement Scope is typed and references Regulation Requirement.
- [ ] Central Account Group Scope is typed and references Account Group.
- [ ] Central Scope command payloads contain no generic `targetType` or `targetId`.
- [ ] Central Scope validity is validated and version-checked.
- [ ] Central Scope delete/restore behavior is explicit.
- [ ] Central changes never physically mutate Local rows.
- [ ] Central Scope UI has typed filtered Value Help and revision-aware mutation feedback.

## 12. Central Coverage acceptance — P3

- [ ] Central Classification connects only scoped Control and Control Objective members from one Central Subprocess Scope.
- [ ] Central Control Objective–Risk Coverage connects only scoped members from one Central Subprocess Scope.
- [ ] Central Control–Risk Coverage connects only scoped members from one Central Subprocess Scope.
- [ ] Requirement–Control Coverage connects only scoped requirement and control members from one Central Subprocess Scope.
- [ ] Central Control–Account Group Coverage connects only scoped members from one Central Subprocess Scope.
- [ ] Same-Subprocess Central Coverage is enforced by database design and service validation.
- [ ] Coverage validity lies within its members' allowed interval.
- [ ] No direct Control–Regulation link exists in table, command, API, UI, or permission vocabulary.
- [ ] No generic coverage endpoint accepts source/target type strings supplied by frontend.
- [ ] Central Coverage UI limits selection to the current Central Subprocess Scope.
- [ ] Central Coverage changes create one Business Revision per command.

## 13. Local Context acceptance — P4

- [ ] Local data exists only under a Local Organization–Subprocess Context.
- [ ] Local Context requires an Organization.
- [ ] Local Context requires a Subprocess, not an arbitrary Process node.
- [ ] Local Context requires the matching Central Subprocess Scope.
- [ ] Composite locality checks prove the Central Scope belongs to the context Subprocess.
- [ ] Local Context has explicit lifecycle, validity, optimistic locking, delete, and restore behavior.
- [ ] No legacy organization-process assignment API or table is used for V2 behavior.
- [ ] Local Context UI clearly shows Organization, Subprocess, Central Blueprint, validity, status, and revision result.
- [ ] Local Context creation does not automatically create Local Scope or Local Coverage facts without an explicit Business Command.

## 14. Local Scope acceptance — P5

- [ ] Local Control Scope belongs to one Local Context and one Central Control Scope origin.
- [ ] Local Control Objective Scope belongs to one Local Context and one Central Objective Scope origin.
- [ ] Local Risk Template Scope belongs to one Local Context and one Central Risk Scope origin.
- [ ] Local Regulation Requirement Scope belongs to one Local Context and one Central Requirement Scope origin.
- [ ] Local Account Group Scope belongs to one Local Context and one Central Account Group Scope origin.
- [ ] Local Scope validity outside Central validity is rejected.
- [ ] Local Scope command payloads contain no generic reference type/id pair.
- [ ] Local Scope rows are not automatically created or updated by Central commands.
- [ ] Local Scope UI requires context selection before typed value help appears.
- [ ] Local Scope mutation returns revision and version data.
- [ ] No Organization-level generic Objective, Risk, Control, Regulation, or Policy assignment remains.

## 15. Local Coverage acceptance — P5

- [ ] Local Classification connects scoped Control and Control Objective members from one Local Context.
- [ ] Local Control Objective–Risk Coverage connects only one Local Context's members.
- [ ] Local Control–Risk Coverage connects only one Local Context's members.
- [ ] Local Requirement–Control Coverage connects only one Local Context's members.
- [ ] Local Control–Account Group Coverage connects only one Local Context's members.
- [ ] Same-context Local Coverage is enforced by database design and service validation.
- [ ] Cross-local-context Coverage returns `CROSS_LOCAL_CONTEXT_COVERAGE`.
- [ ] Local Coverage validity lies within local member and required Central-origin validity.
- [ ] No direct local Control–Regulation relation exists.
- [ ] No generic local relation endpoint exists.
- [ ] Local Coverage UI has context-filtered typed Value Help and conflict handling.

## 16. Policy Scope acceptance — P3 and P5

- [ ] Policy and Policy Version are physically separated.
- [ ] Policy Version is immutable after issue.
- [ ] Frontend cannot choose or modify Policy Version sequence number.
- [ ] Central Policy Scope binds immutable Policy Version to Central Subprocess Scope.
- [ ] Local Policy Scope binds Central Policy Scope to Local Context.
- [ ] Local Policy Scope validity outside Central Policy Scope validity is rejected.
- [ ] Policy Scope does not accept generic target type/id, people arrays, result rows, or workflow state.
- [ ] No Policy approval workflow table, API, page, tab, or permission exists.
- [ ] Policy Scope mutation creates Business Revision and returns version/revision result.
- [ ] Policy Applicability is a read-only query, not a workflow screen.

## 17. Effective acceptance — P7

- [ ] Effective endpoint is read-only.
- [ ] Effective endpoint accepts `evaluationDate` in `YYYY-MM-DD` format.
- [ ] Effective resolution reads Central definition, Scope, Coverage, Local Context, Local Scope, Local Coverage, and Policy Scope facts as needed.
- [ ] Effective query creates no database row, Business Revision, cache row, or local projection row.
- [ ] Effective endpoint returns a dedicated Effective Read DTO.
- [ ] Effective result respects lifecycle and validity dates.
- [ ] Effective result is permission and resource-authorized.
- [ ] Effective UI does not provide inline mutation controls for derived facts.

## 18. Diagnostic acceptance — P7

- [ ] Diagnostic endpoint is read-only.
- [ ] Diagnostic endpoint accepts the common `evaluationDate`.
- [ ] Diagnostic response explains Central/Local origin and validity reasoning.
- [ ] Diagnostic response explains inclusion, exclusion, or missing scope/coverage conditions safely.
- [ ] Diagnostic response returns a dedicated Diagnostic DTO.
- [ ] Diagnostic query creates no Business Revision or stored derived result.
- [ ] Diagnostic endpoint is permission and resource-authorized.
- [ ] Diagnostic UI is an explanation view, not a generic editing form.

## 19. Roll-up acceptance — P7

- [ ] Roll-up endpoint is read-only.
- [ ] Roll-up endpoint accepts the common `evaluationDate`.
- [ ] Roll-up uses approved hierarchy/effective facts only.
- [ ] Roll-up does not calculate or store risk score, likelihood, impact, or control effectiveness.
- [ ] Roll-up returns page/sort metadata for collection responses.
- [ ] Roll-up creates no materialized table, cache table, or revision.
- [ ] Roll-up endpoint is permission and resource-authorized.
- [ ] Roll-up UI has no edit/delete/restore action for derived rows.

## 20. Policy Applicability acceptance — P7

- [ ] Policy Applicability endpoint is read-only.
- [ ] Policy Applicability endpoint accepts the common `evaluationDate`.
- [ ] Policy Applicability considers immutable Policy Version and Central/Local Policy Scope lifecycle/validity.
- [ ] Policy Applicability does not start review, approval, survey, questionnaire, or acknowledgment workflow.
- [ ] Policy Applicability returns no stored derived result or Business Revision.
- [ ] Policy Applicability endpoint is permission and resource-authorized.
- [ ] Policy Applicability UI is read-only and shows explanatory validity/origin facts.
- [ ] Policy Applicability UI does not expose generic target or person assignment editors.

## 21. Security acceptance — P0 through P7

- [ ] Every V2 command has explicit business-permission enforcement.
- [ ] Every V2 resource-specific read/mutation checks resource authorization where required.
- [ ] Control command endpoints no longer rely only on catch-all authentication.
- [ ] Document upload, consume, link, version, purge, and download have separate authorization boundaries.
- [ ] Authorization is resolved from authoritative backend resource identity, not raw frontend target strings alone.
- [ ] Error messages disclose no MinIO credential, bucket, storage locator, or unauthorized resource fact.
- [ ] Permission seeds are remapped to V2 command/read vocabulary.
- [ ] No dead legacy Master Data permission remains after owning feature cleanup.
- [ ] No generic Master Data ACL relation is added to the 47 business tables.
- [ ] Existing cross-cutting ACL/audit facilities are not mistaken for V2 Business Revision or Master Data persistence.
