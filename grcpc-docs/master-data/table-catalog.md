# Master Data V2 Table Catalog

## 1. Catalog status and source discipline

This is the complete Phase 1 physical catalog for the Master Data V2 redesign.

It contains exactly 47 business tables and exactly one technical temporary-upload table.

It is the only table inventory that later Master Data V2 Flyway work may implement.

The `GRC Master Data Final Logical Model` and `GRC Master Data Physical Design Reference` are named by the task as the entity and physical-design authorities.

Those separately named files were not present under `grcpc-docs/master-data/` during the Phase 1 review.

Consequently, physical snake-case names, delegated field sizes, and Oracle constraint expressions below are clearly identified as Phase 1 implementation assumptions where the task did not specify them.

The entity families, exact 47-plus-one boundary, Central/Local separation, typed relations, document model, and revision model are approved task-issued rules and are not legacy-source deductions.

Customer UI DOCX files inform only delegated presentation attributes such as code, title, description, category, dates, assertion, issuer, and document metadata.

Current Java, React, and legacy Flyway source is evidence for deletion and remapping only.

## 2. Shared physical rules

Every business primary key is `id RAW(16) NOT NULL` and is generated by the backend.

API UUID text is converted at the persistence boundary; no business UUID is stored as `VARCHAR2(36 CHAR)`.

`created_at` and `updated_at` use `TIMESTAMP(6) WITH TIME ZONE`.

`created_by`, `updated_by`, `deleted_by`, and an acting-user field use `RAW(16)` without introducing a Master Data user foreign-key table.

Business dates use Oracle `DATE` and represent whole calendar dates.

Technical instants use `TIMESTAMP(6) WITH TIME ZONE`.

Mutable business tables have `version NUMBER(19) NOT NULL` with default zero.

Explicit soft deletion uses nullable `deleted_at TIMESTAMP(6) WITH TIME ZONE` and `deleted_by RAW(16)`.

An explicit restore clears those two fields through a version-checked business command.

No table relies on hidden `@SQLDelete` behavior.

Where a table has a business code, its unique constraint includes deleted records because it is an unconditional unique constraint.

`valid_from DATE` and `valid_to DATE` use `CHECK (valid_to IS NULL OR valid_from IS NULL OR valid_to >= valid_from)` when validity is meaningful.

`status` is a lifecycle value, not a workflow engine state.

All foreign-key indexes are required unless covered by an equivalent composite index shown in the entry.

All names and column sizes below are Oracle 19c-compatible implementation assumptions pending direct reconciliation with the absent Physical Design Reference file.

## 4. Structural and Central Definitions

### B01 — `organization`

- **Purpose:** Stores the Central organization hierarchy used to establish a Local Organization–Subprocess Context; it is not a parent of Central definitions.
- **Table family:** Structural and Central Definitions.
- **Primary key:** `id RAW(16) NOT NULL`.
- **Business key:** `code VARCHAR2(64 CHAR) NOT NULL`; unconditional `UNIQUE (code)` includes soft-deleted rows.
- **Foreign keys:** nullable `parent_organization_id RAW(16)` references `organization(id)`.
- **Composite foreign keys:** None.
- **Lifecycle fields:** `status VARCHAR2(30 CHAR) NOT NULL`, `deleted_at`, `deleted_by`, `created_at`, `created_by`, `updated_at`, and `updated_by`; `status` is restricted to approved active/inactive lifecycle values.
- **Validity fields:** nullable `valid_from DATE` and `valid_to DATE` with the shared valid-range check.
- **Optimistic-lock field:** `version NUMBER(19) NOT NULL`.
- **Important business attributes and Oracle types:** `name VARCHAR2(255 CHAR) NOT NULL`, `organization_type VARCHAR2(40 CHAR) NOT NULL`, `location VARCHAR2(255 CHAR) NULL`, and `description VARCHAR2(2000 CHAR) NULL`.
- **Nullability:** only identity, code, name, organization type, lifecycle state, creation metadata, and version are required; parent, description, location, validity, update metadata, and delete metadata are nullable.
- **Unique and check constraints:** `uq_organization_code`; parent cannot equal id; `chk_organization_valid_range`; type and status check lists are closed implementation enums.
- **Required indexes:** unique code, `parent_organization_id`, `(status, deleted_at)`, and `(name, deleted_at)`.
- **Mutability:** hierarchy and descriptive fields are mutable through version-checked commands; delete and restore are explicit; identity and code are never recycled.
- **Business Revision participation:** yes; create, update, move, status, delete, and restore each create one backend-owned revision.
- **Authoritative source:** Conceptual Model business boundary; Final Logical Model entity; customer `سازمان - فرم ایجاد اطلاعات پایه- Master Data  .docx` for delegated name/type/location/description fields.
- **Assumptions:** code length, status vocabulary, and self-parent check are physical implementation assumptions because the Physical Design Reference file was absent.

## 5. Central Scope, Classification, Policy Scope, and Coverage

Central tables use `central_subprocess_scope_id` as their locality key.

Every typed Central scope table has an additional unconditional `UNIQUE (id, central_subprocess_scope_id)` solely to support the composite foreign keys in classification and coverage tables.

Those composite foreign keys make a cross-Subprocess Central Coverage physically impossible without weakening the model.

- **Table family:** Document.
- **Primary key:** `id RAW(16) NOT NULL`.
- **Business key:** `document_id RAW(16) NOT NULL` plus `version_number NUMBER(10) NOT NULL`; `UNIQUE (document_id, version_number)`.
- **Foreign keys:** `document_id` references `document(id)`; `created_revision_id RAW(16) NOT NULL` references `business_revision(id)` after the revision core is created.
- **Composite foreign keys:** None.
- **Lifecycle fields:** immutable `created_at`, `created_by`, `created_revision_id`, nullable `purged_at`, `purged_by`, and `purge_reason VARCHAR2(1000 CHAR)`; no general soft delete or content update exists.
- **Validity fields:** none; validity of a business document belongs to `document`, Policy Version, or the linked aggregate as appropriate.
- **Optimistic-lock field:** none after creation because the version payload is immutable; the parent Document command is version-checked before adding a version.
- **Important business attributes and Oracle types:** `original_filename VARCHAR2(500 CHAR) NOT NULL`, `media_type VARCHAR2(255 CHAR) NOT NULL`, `size_bytes NUMBER(19) NOT NULL`, `sha256 RAW(32) NOT NULL`, `storage_locator VARCHAR2(1024 CHAR) NOT NULL`, and `retention_class VARCHAR2(80 CHAR) NULL`.
- **Nullability:** document, version number, creation revision, filename, media type, size, hash, storage locator, and creation facts are required; retention data and purge facts are nullable.
- **Unique and check constraints:** `uq_document_version_number`, `size_bytes >= 0`, `version_number > 0`, and a purge-state consistency check requiring all purge fields together.
- **Required indexes:** `(document_id, version_number)`, `created_revision_id`, `sha256`, and `(purged_at)` for lifecycle cleanup or download protection.
- **Mutability:** payload metadata and locator are immutable; a dedicated authorized purge operation changes only the allowed purge lifecycle facts and thereafter causes the `purged Document Version` error.
- **Business Revision participation:** yes; creation and purging are represented in backend-owned revision content.
- **Authoritative source:** Conceptual shared Document and Business Revision; Final Logical Model Document Version; Physical Design Reference MinIO rule; customer documents for version/file metadata intent.
- **Assumptions:** a database locator is opaque and is never returned in API responses; environment bucket configuration stays outside this table.

### B45 — `document_link`

- **Purpose:** Associates an immutable Document Version with an approved Master Data aggregate through the first and only document-target controlled polymorphism.
- **Table family:** Document.
- **Primary key:** `id RAW(16) NOT NULL`.
- **Business key:** `target_aggregate_type VARCHAR2(80 CHAR) NOT NULL`, `target_aggregate_id RAW(16) NOT NULL`, `document_version_id RAW(16) NOT NULL`, and `link_role VARCHAR2(60 CHAR) NOT NULL`; `UNIQUE` across those four fields.
- **Foreign keys:** `document_version_id` references `document_version(id)`; the controlled target is deliberately not a relational FK because it is one of the two approved controlled polymorphisms.
- **Composite foreign keys:** None for controlled target; application validation resolves the target against an allow-list and its resource authorization boundary.
- **Lifecycle fields:** `status VARCHAR2(30 CHAR) NOT NULL`, explicit delete metadata, creation/update metadata, and `version NUMBER(19) NOT NULL`.
- **Validity fields:** `valid_from DATE NULL`, `valid_to DATE NULL`, and shared valid-range check when a link has an effective period.
- **Optimistic-lock field:** `version NUMBER(19) NOT NULL`.
- **Important business attributes and Oracle types:** target type, target id, link role, `link_note VARCHAR2(2000 CHAR) NULL`, and `display_order NUMBER(10) NULL`.
- **Nullability:** target type/id, document version, link role, status, creation metadata, and version are required; note, display order, validity, updates, and delete metadata are nullable.
- **Unique and check constraints:** `uq_document_link_target_version_role`, valid-range check, and `chk_document_link_target_type` closed to cataloged Master Data aggregate types; no arbitrary caller-supplied type is accepted.
- **Required indexes:** `(target_aggregate_type, target_aggregate_id, status, deleted_at)`, document version, link role, and validity-date index.
- **Mutability:** version-checked link lifecycle only; changing file content creates a new Document Version and a deliberate link command, never a mutation of the old version.
- **Business Revision participation:** yes.
- **Authoritative source:** Conceptual shared Document concept; Final Logical Model Document Link; Physical Design Reference controlled MinIO/document rules; all customer mock-ups for document-tab visual intent.
- **Assumptions:** target types include only approved V2 aggregates and typed relation aggregates; the allow-list is owned by the Master Data domain, not a generic attachment framework.

## 8. Business Revision

Business Revision is a business-history mechanism, not a substitute for audit logging.

`revision_content` is the second and only other controlled-polymorphic table in the redesign.

### B46 — `business_revision`

- **Purpose:** Records the backend-owned immutable revision created for each successful Master Data Business Command.
- **Table family:** Business Revision.
- **Primary key:** `id RAW(16) NOT NULL`.
- **Business key:** `revision_sequence NUMBER(19) NOT NULL` with unconditional `UNIQUE (revision_sequence)`; `command_id VARCHAR2(100 CHAR) NULL` is unique when supplied for safe idempotency.
- **Foreign keys:** none to an unapproved user table; `actor_id RAW(16) NOT NULL` is an identity reference owned by cross-domain security.
- **Composite foreign keys:** None.
- **Lifecycle fields:** immutable `applied_at TIMESTAMP(6) WITH TIME ZONE NOT NULL`, `actor_id`, `domain VARCHAR2(80 CHAR) NOT NULL`, `command_type VARCHAR2(120 CHAR) NOT NULL`, `command_id`, and `correlation_id VARCHAR2(100 CHAR) NULL`; it has no delete, restore, or mutable status.
- **Validity fields:** none.
- **Optimistic-lock field:** none after creation; this immutable ledger record is written in the same backend-owned transaction as the command result.
- **Important business attributes and Oracle types:** `revision_sequence NUMBER(19)`, command/domain names, actor, correlation id, and optional `request_fingerprint RAW(32)` for idempotency verification.
- **Nullability:** sequence, applied-at, actor, domain, and command type are required; command id, correlation id, and fingerprint are nullable unless an idempotent command supplies them.
- **Unique and check constraints:** `uq_business_revision_sequence`, nullable `uq_business_revision_command_id`, positive sequence check, and a closed domain check.
- **Required indexes:** sequence, `(domain, applied_at)`, actor, command id, and correlation id.
- **Mutability:** immutable; an applied revision is never deleted, restored, amended, or repurposed.
- **Business Revision participation:** this is the root record; exactly one is created by every successful Business Command.
- **Authoritative source:** Conceptual Model Business Revision; Final Logical Model Business Revision; task-issued backend ownership and transaction rules.
- **Assumptions:** a global monotonic sequence is implementation-owned by the backend and is never supplied by the frontend.

### B47 — `revision_content`

- **Purpose:** Stores immutable before/after content for the aggregates affected by a Business Revision through the second approved controlled polymorphism.
- **Table family:** Business Revision.
- **Primary key:** `id RAW(16) NOT NULL`.
- **Business key:** `business_revision_id RAW(16) NOT NULL` plus `content_sequence NUMBER(10) NOT NULL`; `UNIQUE (business_revision_id, content_sequence)`.
- **Foreign keys:** `business_revision_id` references `business_revision(id)`; aggregate identity is intentionally controlled polymorphism and has no generic relational FK.
- **Composite foreign keys:** None for aggregate target; closed aggregate-type validation and domain-match validation are mandatory in the application and may be reinforced by a check constraint.
- **Lifecycle fields:** immutable creation by the revision transaction; no status, soft-delete, restore, or mutable audit columns are allowed beyond creation facts.
- **Validity fields:** none.
- **Optimistic-lock field:** none after creation because Revision Content is immutable.
- **Important business attributes and Oracle types:** `aggregate_type VARCHAR2(80 CHAR) NOT NULL`, `aggregate_id RAW(16) NOT NULL`, `operation VARCHAR2(40 CHAR) NOT NULL`, `before_snapshot CLOB NULL`, `after_snapshot CLOB NULL`, and `content_hash RAW(32) NOT NULL`.
- **Nullability:** revision, sequence, aggregate type/id, operation, and hash are required; a create may have null before snapshot and a delete may have null after snapshot.
- **Unique and check constraints:** unique revision/sequence, positive sequence, closed operation check, closed aggregate-type check, and a snapshot-presence check appropriate to the operation.
- **Required indexes:** business revision, `(aggregate_type, aggregate_id)`, operation, and content hash.
- **Mutability:** immutable; frontend requests never contain these snapshots, sequence values, hashes, or aggregate-type authorizations.
- **Business Revision participation:** it is the child record of the revision root and stores all affected aggregates for that command.
- **Authoritative source:** Conceptual Model Business Revision; Final Logical Model Revision Content; task-issued controlled-polymorphism limit.
- **Assumptions:** JSON or structured text snapshot format remains an internal backend serialization contract and is never a frontend-created payload.

## 9. Technical Temporary Upload

### T01 — `document_temp_upload`

- **Purpose:** Is the single technical table that records a temporary MinIO upload before a parent Business Command creates a Document Version.
- **Table family:** Technical Temporary Upload.
- **Primary key:** `id RAW(16) NOT NULL`; this is the backend-issued `tempUploadId` exposed to the API.
- **Business key:** `storage_locator VARCHAR2(1024 CHAR) NOT NULL`; `UNIQUE (storage_locator)` prevents accidental duplicate object tracking.
- **Foreign keys:** nullable `consumed_revision_id RAW(16)` references `business_revision(id)` after successful consumption; it has no target-type/target-id foreign key.
- **Composite foreign keys:** None.
- **Lifecycle fields:** `state VARCHAR2(30 CHAR) NOT NULL`, `created_at`, `uploaded_at`, `expires_at`, `consumed_at`, `consumed_revision_id`, `expired_at`, and `discarded_at`; no soft-delete/restore applies because technical uploads expire or are consumed.
- **Validity fields:** none; `expires_at` is a technical timestamp, not a business validity date.
- **Optimistic-lock field:** `version NUMBER(19) NOT NULL` to protect one-time consumption and cleanup races.
- **Important business attributes and Oracle types:** `original_filename VARCHAR2(500 CHAR) NOT NULL`, `media_type VARCHAR2(255 CHAR) NOT NULL`, `size_bytes NUMBER(19) NOT NULL`, `sha256 RAW(32) NOT NULL`, `uploaded_by RAW(16) NOT NULL`, and opaque `storage_locator VARCHAR2(1024 CHAR) NOT NULL`.
- **Nullability:** id, state, upload/creation/expiry timestamps, file metadata, hash, uploader, storage locator, and version are required; consumption/expiry/discard facts are nullable until their state occurs.
- **Unique and check constraints:** unique storage locator, `size_bytes >= 0`, `expires_at > uploaded_at`, closed states `ACTIVE`, `CONSUMED`, `EXPIRED`, and `DISCARDED`, and state/fact consistency checks; there is no `temp_session_id` column.
- **Required indexes:** `(state, expires_at)`, uploaded-by, checksum, consumed revision, and unique locator.
- **Mutability:** only the backend moves an upload from ACTIVE to CONSUMED, EXPIRED, or DISCARDED; consuming is idempotent only for the same command identity and otherwise returns already-consumed error.
- **Business Revision participation:** indirect; a successful consuming command links it to the created Business Revision, while uploading alone does not create a business revision.
- **Authoritative source:** Physical Design Reference temporary-upload rule; task-issued `tempUploadId`, one-time consumption, and no distributed Oracle–MinIO transaction rules; current document code only as legacy replacement evidence.
- **Assumptions:** state facts support recoverable MinIO compensation without introducing another technical table, scheduler table, outbox, or cache table.
